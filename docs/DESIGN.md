# Cherry BiM: архитектура

Версия формата 0.1. Документ объясняет решения, которые дорого менять потом, и как формат соотносится со стандартами.

## Задача

Одна модель для всех масштабов жилья и всех потребителей:

- модуль Home Assistant с 3D-планом и учётом вещей;
- бот жильцов с картой квартала;
- голосовой помощник через MCP;
- выгрузки в BIM- и ГИС-программы.

Это не BIM-редактор. Это компактный JSON с выгрузками в стандарты.

Формат проверен на реальной квартире и квартале (сами данные не публикуются):

- 174 сущности в двух пакетах;
- шкаф из OpenFurnitureMaker разложен на секции, 9 ящиков и отделения;
- фасад квартиры после привязки совпал с контуром дома до сотых градуса;
- выгрузка IFC4 проходит проверку схемы IfcOpenShell без ошибок.

## Решения

1. **Дерево вложенности как в IFC.**
   - Цепочка: site → building → section (подъезд) → storey → unit (квартира) → space (комната) → furniture → storage → item.
   - Подъезд выгружается как `IfcBuilding` с CompositionType = PARTIAL, квартира — как `IfcSpace` с CompositionType = COMPLEX, объединяющий комнаты.
2. **Своя система координат у каждого уровня.**
   - `placement` = сдвиг + поворот вокруг Z относительно родителя.
   - Метры, ось Z вверх, правая система. Геометрия лежит в собственной системе сущности.
   - Участок привязан к Земле точкой `georef` (WGS84 и локальная ENU).
3. **Стабильные id.**
   - Импортированное получает `uuid5(пространство, key)`: пересборка даёт те же id, пакеты ссылаются друг на друга без поиска.
   - Ручное получает случайный UUID (позже UUIDv7).
   - IFC GlobalId выводится без потерь (`ifc_guid`, совпадает с `ifcopenshell.guid.compress`).
4. **Приватность у каждой сущности.**
   - Уровни public → residents → household → owner → secret, наследуются внутри пакета.
   - Выгрузки получают аудиторию. Пакеты разделены по владельцам.
5. **Федерация без сервера.** Пакет квартиры ссылается на этаж из пакета квартала по id. Владелец квартиры хранит свой пакет, пакет квартала ведёт его хозяин.
6. **Происхождение и точность.** Например, `src: {from: "project:OV-10a", acc: 0.5}`. Схематичное не выдаётся за точное.
7. **Внешние системы — через `bind`.** Например, `ha.entity`, `osm.way`, `dreame.segment`, `brti.room`. Ядро о них не знает, адаптеры живут в приложениях.
8. **Одна точка правды для схемы.** pydantic-модели → JSON Schema (`schema/`) → типы для других языков.

## Модель

| Поле | Смысл |
|---|---|
| `id`, `key` | UUID и человекочитаемый ключ |
| `kind`, `type` | Вид и подтип из словаря `schema/kinds.json` |
| `parent` | Вложение |
| `placement`, `geom` | Положение и геометрия: `extrusion`, `box`, `polyline`, `point`, `mesh` |
| `props` | Площади, артикулы, номиналы |
| `bind` | Связи с внешними системами |
| `refs` | `feeds`, `controls`, `has_member`, `stacked_above`… |
| `privacy`, `src`, `tags`, `aliases` | Видимость, происхождение, теги, синонимы для поиска и голоса |

## Стандарты (октябрь 2026)

| Стандарт | Состояние | Использование |
|---|---|---|
| IFC 4.3 (ISO 16739-1:2024) | Действует | Цель выгрузки. Сейчас пишем IFC4 (запасной вариант). Отличия 4.3: `IfcDistributionBoard`, `Pset_SpaceCommon.IsExternal` |
| IFC5 / IFCX | Альфа, основа не утверждена | Идеи без синтаксиса: дети по именам, атрибуты с пространствами имён, слои-наложения |
| GeoJSON, IMDF 1.0 | Стабильны | 2D-карты квартала и общих зон (MapLibre, Leaflet) |
| glTF 2.0 | Стабилен | 3D в браузере. IFC → GLB на сервере через IfcOpenShell |
| CityJSON 2.0 | OGC | Район: здания, `BuildingUnit` для квартир |
| Brick 1.4 | Стабилен | Подсказка класса у помещений и устройств |

Привязка района и IFC: `IfcMapConversion` в проекции UTM 35N (EPSG:32635) для Беларуси и соседей. Обычно — UTM своей зоны.

IfcOpenShell (LGPL) — необязательная зависимость. На Alpine он не ставится (нет колёс musllinux), поэтому выгрузку в контейнере делаем на Debian.

## Сервер (0.2)

`cherrybim.server` — один процесс на Starlette и uvicorn, экстра `server`. Им же собран аддон Home Assistant.

```
браузер (three.js) ──HTTP /api/*, WebSocket /api/live──┐
голосовой ассистент ──MCP /mcp (streamable HTTP)───────┤── Server ── Store ── *.twin.json (только чтение)
                                                       │                 └── items.twin.json, trash.jsonl
Home Assistant ◄── REST (службы), WebSocket (state_changed) ── HA
```

- **Пакеты** лежат в папке и только читаются; их пересобирают скриптом и подкладывают заново, сервер замечает новое время файла. **Вещи** — отдельный пакет `items.twin.json` в папке данных: его правят API и MCP, запись атомарная, вычеркнутое уходит строкой в `trash.jsonl`. Поправили файл руками — сервер перечитает его, а не затрёт.
- **Поиск** (`Twin.rank`): слово в названии и синонимах — 3 очка, в названиях родителей и того, на что ссылается сущность, — 2 («ящик 2 в спальне», «обои в спальне»), в тегах и свойствах — 1; найдены все слова — ещё 10. Однобуквенные слова необязательны: «в» — предлог, «секция б» — метка. Место для вещи выбирается только при полном совпадении, ничья — «уточни, какой именно».
- **MCP**: `find`, `contents`, `add_item`, `move_item`, `remove_item`, `show`, `documents`. Без сессий и с JSON-ответами: клиент HA открывает новую сессию на каждый вызов. Ответы — короткий русский текст с путём от комнаты, его можно читать вслух.
- **Живые состояния.** Сервер подписывается на `state_changed` и пересылает браузерам только привязанные сущности (`bind["ha.entity"]`). Пылесос: `bind["dreame.affine"]` — аффинное преобразование системы квартиры в миллиметры робота; по нему сервер ставит робота на 3D-план и шлёт `vacuum_goto` в точку, по которой щёлкнули.
- **Доступ.** Вход только с адресов из `--allow` (в аддоне — сеть Supervisor). Отсюда можно щёлкать лишь `light`, `switch`, `fan` из привязок; замков нет.
- **Просмотрщик** — статичные файлы (`static/`, three.js 0.170 и нужные модули `examples/jsm` лежат рядом), все адреса относительные, поэтому страница работает и под ingress. Виды «Квартира», «Дом», «Квартал»; срез стен на 1,15 м; выбранный шкаф и шкаф с выбранным ящиком полупрозрачны, повторный щелчок проваливается шкаф → секция → ящик; ящик показывается спереди (фасад мебели — сторона −Y её системы). Подробнее — ниже, «Реалистичная геометрия (0.4)».

### Реалистичная геометрия (0.4)

Форма — как у настоящей вещи, поверхности — без текстур: цвет, шероховатость, металл. Объём дают свет и тени, а не картинки.

- **Модели по типам** (`static/families.js`). Пакет хранит только габариты (`box`) или точку и тип; модель строится из них при загрузке. Например, `furniture.bed` — царга, матрас, одеяло, подушки и изголовье у стороны +Y; `opening.window` — рама, створки со стеклом и ручками, подоконник, стена под окном и над ним. Тип без своей модели рисуется прежней коробкой. Детали сливаются по материалам (`static/kit.js`): у сложной мебели несколько вызовов отрисовки.
- **Ориентация.** Фасад — сторона −Y системы сущности, как у мебели из OpenFurnitureMaker. У проёма X идёт вдоль стены, −Y — сторона комнаты, у двери — сторона, куда она открывается. Старые пакеты, где коробка проёма лежит поперёк стены, разворачиваются по контуру квартиры: снаружи — улица.
- **Подсказки отрисовки** — словарь `props.render`. Это не данные о вещи, поэтому их нет в карточке, в поиске и в ответах ассистента:
  - `colors` — цвета частей: `{"body": "#b39069", "front": "#75805c", "*": "#ffffff"}`;
  - у дверей `hinge` (`left`/`right` — где петли, если смотреть со стороны открывания), `open` (угол, градусы), у балконного блока `leaf` (ширина створки);
  - у мебели `handles` (`gola`, `bar`, `knob`, `none`), у шкафа `fronts` — двери `{"x": [x0, x1], "z": [z0, z1], "hinge": …, "handle": [x, z0, z1]}` и `fillers` (из проекта OFM: `io_ofm.facade_from_ofm`);
  - у места хранения `front` — что спереди: `drawer`, `door`, `open`, `shelf`, `hooks`, `none`;
  - у отделки `on` — куда ложится (`floor`, `walls`, `skirting`, `ceiling`): пол комнаты красится по ней, плинтус ставится вдоль стен;
  - у отопительного прибора `style` (`panel`, `convector`), у окна `sashes` (число створок) и `railing` (ограждение снаружи «французского» окна), у зеркала `frame`, `shelf`, `backlight`;
  - у мебели `legs` (`wood`, `casters`, `plinth`, `short`, у стола `panel`, `splay`, `trestle`; `false` — без ножек), у корпусной мебели `cells` — ячейки фасада `[u0, v0, u1, v1, вид, петли]` в долях ширины и высоты; у обеденного стола `table_w`, `table_l`, `chairs_per_side`, `chairs_at_ends`, `chair_out` (число или `{side, ends}`); у кухни `strips` (полосы между ярусами, `[z0, z1, часть, x0, x1]`), `counter` (`[x0, x1]` — столешница не на всю ширину, в углу её кладёт соседний модуль) и `backsplash` (`{top, x}`); у штор `panel` (ширина полотна или пара `[левое, правое]`); у двери шкафа `handle: false` — без ручки;
  - у места хранения ещё `piece` (части одного предмета стоят на общих ножках и под общей крышкой), `pitch` и `count` у крючков, `leaves`, `hinge`, `shelves`, `inlay` (вкладной фасад между боковинами), `at` и `handle_len` (где и какой длины ручка дверцы), у полки `board` (толщина) и `brackets: false`;
  - формы отдельных вещей: у дивана `arms: false`, `bolster` (и `bolster_inset` — отступ валика от задней грани), `back: "tufted"` (цельная стёганая спинка во всю ширину; `seams_v`, `seam_h` — швы), `seats`, `arm_w`, `arm_r`, `arm_h`; у корпусной мебели на колёсиках и ножках `base` (их высота) и `leg_inset`, у банкетки `leg_inset`, у пуфа `legs_h`, у прихожей `legs: "splay"`; у места хранения-штанги `board` (доска под ней); у ящика `handle_len`; у кухонного модуля `joint` (тёмная стыковочная планка у начала столешницы); у двери `jamb_top`, `leaf_w`, `leaf_inset` (полотно утоплено в проём), `latch: false` (без планки замка на торце); у штор `tulle_span`, `hem`, `top`, `finial: "cube"`; у станции робота `body_d` (глубина колонны); у 3D-принтера `spool_w`, `spool_r`; у МФУ цвет `adf` (лоток автоподатчика); у светильника `drop` (висит ниже), `rays` (`[[угол°, длина], …]`), у решётки `spacing`; у места хранения прихожей `setback` (часть утоплена от фасада); у двери `frame_inset` (коробка уже проёма, по бокам полосы стены), `frame_h`, `sill` (порог), `casing_over` (наличник поверх коробки); у МФУ `band`, `slot: false`, `tray`; у штор `panel_depth`, `skirt_opacity`; у навесного модуля `underside: "inset"` (дно за фасадами); у банкетки `legs_dy`, `splay`; у корпусной мебели по ячейкам `handle_len`; у стола `drawers` (`[[x0, x1], …]` — ящики под столешницей) и `panel_inset` (`[слева, справа]` — боковины отступают от торцов), у стола с ножками-полосами `leg_inset` и `splay`; у ящика `handle_at: "middle"`, `lock`, ручки `handles: "arch"`; у крючков `first`; у зеркала `inset` (`[бока, низ, верх]`, цвет стекла — `colors.glass`); у двери `jamb` (ширина коробки), `casing_w` (наличника), `handle_z`, `escutcheon: "plate"`, `rosette: "round"`, у входной `peephole`; у штор `tulle_opacity` и `tulle_skirt` (`[x0, x1, y, z]` — тюль перекинут через прибор под окном); у лежанки `bolster`, `rim_w`; у кольцевого светильника `tilt` (наклон внешнего кольца); у офисного кресла `armrests: false`, `headrest: false` (высокая спинка); у шкафа `socle` и `socle_inset`; у кухонного модуля `plinth: 0` и `underside` (дно навесного модуля цветом `colors.underside`: видно снизу и кромкой 18 мм под фасадами; столешница свешивается над фасадами на 10 мм); у прихожей `panel_frame` (рамка вешалки: стойки, перекладины, рейки); у банкетки `lid`; у монитора `curved`, `screen_h`; у системного блока `fans: false` (подсветка за стеклом); у лампы `shape: "stick"`; у роутера `antennas`; у колонки `shape` (`cube`, `screen`); у холодильника `handles: "none"`, `display`; у духовки `knobs: false`; у микроволновки `style: "glass"`; у мойки `dispenser`; у базы пылесоса `robot`; у балконного блока `panel` (высота филёнки створки, 0 — остеклена до низа; глухая часть — стекло прямо в раме); у штор `rod` (штанга шире полотен) и `fold` (глубина складок); у кольцевого светильника `diameter`; у подсветки (`device.backlight`) `strips` — светящиеся полосы в системе прибора;
  - у светильника `fixture` (`grid`, `rays`, `ring`, `disc`, иначе плафон), `angle` — поворот от осей комнаты, `diameter` — длина планок решётки, размах лучей или диаметр диска и колец. Светильник с `placement`, но без коробки, висит в этой точке, иначе — в центре комнаты.
- **Буфер глубины.** В виде квартиры ближняя и дальняя плоскости камеры 0,05 и 300 м (в виде дома и квартала — 0,3 и 5000): иначе за тонкой стеной проступает силуэт вещи из соседней комнаты. `?msaa=0` выключает сглаживание в буфере кадра: программный WebGL (SwiftShader) пропускает в MSAA-буфере кромки закрытых вещей; сверочные рендеры поэтому идут без MSAA с двойной плотностью пикселей и уменьшаются.
- **Свет.** Окружение комнаты из примитивов three.js (`RoomEnvironment`) для отражений, солнце с мягкими тенями, затенение углов GTAO, нейтральный тонмаппинг. Холст прозрачный: фон — цвет темы страницы; цвета в буфере умножены на альфу, и перед тонмаппингом умножение снимается, иначе стекло поверх фона светлеет ореолом.
- **Срез.** Стены — призмы, их срез — масштаб по Z. У проёмов (рамы, створки, полотна) две сборки, целая и обрезанная на 1,15 м.
- **Потолок.** В виде квартиры без среза у комнат есть потолок на высоте потолка квартиры. Он виден только снизу, поэтому сверху на квартиру не мешает. Стены и проёмы в этом виде не отбрасывают тень от «солнца» внутрь комнат: в настоящей комнате свет рассеянный.
- **Стыки и щели.** Грань стены, которая упирается в соседнюю стену или в коробку двери, не строится. Иначе её ребро лежит в плоскости лицевой грани соседа, бьётся с ней по глубине и рисует на стене светлый пунктир. Куски стены в проёмах (перемычка, стена под окном, коробка двери) утоплены на 0,5 мм, наличник отстоит от стены на 1 мм, пол в проёме на 0,5 мм ниже пола комнат и заходит под него — по той же причине. В щель у косяка видна «заглушка» внутри стены. Двусторонние материалы для этого не годятся: обратная сторона соседней грани выигрывает на ребре и рисует тот же пунктир. За фасадами мебели и дверями шкафов — тёмная подложка: щель между фасадами видна сплошной тёмной линией.
- **Плинтус** обходит стены комнаты и кончается у наличника двери, а не у проёма; в проходе без двери идёт по обоим откосам.
- **Скрытое и состояние.** Трубы и кабели в стенах и стяжке видны в режиме «Инженерия» рентгеном: копия меша рисуется только там, где её закрывают. Устройство без места в комнате — маленький индикатор; у светильника — светильник своего вида у потолка (тени не отбрасывает), на срезе — тонкое кольцо на полу под ним, включённый свет — пятно на полу комнаты.
- **Экраны.** Выключенный экран ТВ и станции тёмный — и без Home Assistant; включённый красится по состоянию.
- **Встроенная техника.** Колонны и навесные шкафы — сплошной корпус, поэтому духовка, микроволновка и подобная техника ставятся фасадом в плоскость корпуса: их стекло выступает вперёд, как у настоящей встройки, и не мерцает вместе с гранью корпуса.
- **Нагрузка.** Квартира на 200 сущностей — около 400 мешей, 1,5 тыс. вызовов и 220 тыс. треугольников за кадр вместе с тенью и затенением углов. Кадр рисуется только при изменениях; если он стабильно дольше 30 мс, просмотрщик отключает затенение углов, потом снижает плотность пикселей.
- **Честность.** Модель не выдумывает того, чего нет в данных: окна на фасадах домов не рисуются (их положение неизвестно), устройство без координат не ставится в угол комнаты как настоящее.

### Документы у сущностей

У любой сущности — своя база документов: инструкции, проект и чертежи, чеки, гарантии, договоры, страницы магазина.

- **Документ** — сущность вида `document` (`docs.py`, IFC — `IfcDocumentReference`). Родитель — то, к чему он относится (холодильник, кухня, шкаф). Если документ описывает и другие вещи, у него связи `documents` (проект кухни → все её модули). Подтипы: `project` (проект, чертежи), `assembly` (инструкция по сборке, монтажу), `manual`, `datasheet`, `receipt`, `warranty`, `contract`, `page` (страница сайта), `photo`, `note`.
- **Ссылка и копия.** `props.url` — где документ в сети; `props.file` — локальная копия, путь от корня папки документов (`--docs`, по умолчанию `DATA/docs`); ещё `mime`, `size`, `pages`, `sha256`, `saved_at`. Копия открывается, даже если сайт пропал или переделан. Пакет хранит только путь, файлы лежат рядом с пакетами и в git не нужны.
- **Где видно.** В карточке — «Документы»: свои и документы ближайшего родителя на всё целое (`project`, `assembly`, `contract`): у ящика кухни — проект кухни, а чек на розетку кухни — только у розетки. Наследуют части, а не вещи, которые там лежат: у телефона в ящике проекта кухни нет. Документ, который уже есть в своих (проект кухни связан с её модулями), второй раз «у родителя» не повторяется. Карточка документа: открыть копию, скачать, на сайт, к чему относится; кнопки копии — только если сервер нашёл файл в папке документов (`copy` в снимке). Видно и считается (`find`: «документов: N») только то, что открыто аудитории; закрытое не находится и по id.
- **Добавить из просмотрщика**: файлом (`POST /api/docs?to=…&title=…&type=…&filename=…`, тело — файл до 50 МБ; `filename` обязателен, поэтому файл `.json` не путается с запросом) или ссылкой (`POST /api/docs` с JSON `{to, title, type, url, copy}`): при `copy` сервер скачивает копию сам — PDF и картинки как есть, страницу HTML-копией с `<base href>`, переведённой в UTF-8 из её кодировки. Тип копии — по содержимому, а не по адресу: PDF со страницы `download.php` ляжет как `.pdf`. Такие документы пишутся в пакет вещей, убираются в `trash.jsonl`; вычеркнули вещь — её документы уходят в ту же строку корзины. `GET /api/doc/{id}` отдаёт копию с адреса просмотрщика, а под ingress это адрес самого HA, поэтому из копии ничего не выполняется: PDF, картинки и текст открываются во вкладке, страница и SVG — в песочнице (`Content-Security-Policy: sandbox`), остальное (XML, офисные файлы, неизвестное) — только скачать. Путь копии не выходит за папку документов.
- **Копии страниц при сборке пакетов**: `python -m cherrybim.docs snapshot URL файл.pdf` — Chrome без окна по протоколу отладки печатает экранную вёрстку в PDF с текстом, предварительно убрав всплывающие окна и затемнение. Печатную вёрстку магазины часто прячут целиком, поэтому `--print-to-pdf` давал пустую страницу. `fetch` — скачать файл как есть.
- **Закрытые номера** (IMEI, серийный номер, MAC) — словарь `props.ids` у самой вещи. Его нет в поиске (индексируются только строковые свойства) и в ответах ассистента; в карточке номер скрыт (видны последние 4 знака у длинного, 2 — у серийного из 8–11, короткий — целиком), «показать» — по кнопке, второй щелчок копирует. У вещей из пакета вещей номера правятся в «Изменить»: строка «название: номер», второй IMEI сохраняется как «IMEI 2»; название до 40 знаков, номер до 120.
- **Голос.** MCP-инструмент `documents(what)`: «какие документы, инструкции, чертежи есть у …» — названия, типы, есть ли копия, ссылки. `find` сообщает, сколько у сущности документов.

- **План картинкой** (`plan.py`, 0.3). Pillow, рисуется вдвое крупнее и уменьшается. Вместилище — квартира места, иначе этаж, иначе квартал. Рисуются только видимые аудитории сущности, мебель внутри мебели сверху пропускается. На экран план попадает так: сервер кладёт PNG в медиа HA и зовёт скрипт `--show-script`. Что дальше делает скрипт (например, ставит запрос в очередь ТВ), ядро не знает.
