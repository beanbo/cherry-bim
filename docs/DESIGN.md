# Cherry BiM: архитектура

Версия формата 0.1. Документ объясняет решения, которые дорого менять потом, и как формат соотносится со стандартами.

## Задача

Одна модель для всех масштабов жилья и всех потребителей:

- модуль Home Assistant с 3D-планом и учётом вещей;
- бот жильцов с картой квартала;
- голосовой помощник через MCP;
- выгрузки в BIM- и ГИС-программы.

Это не BIM-редактор. Это компактный JSON с выгрузками в стандарты.

Формат проверен на реальной квартире и квартале (сами данные не публикуются):

- 174 сущности в двух пакетах;
- шкаф из OpenFurnitureMaker разложен на секции, 9 ящиков и отделения;
- фасад квартиры после привязки совпал с контуром дома до сотых градуса;
- выгрузка IFC4 проходит проверку схемы IfcOpenShell без ошибок.

## Решения

1. **Дерево вложенности как в IFC.**
   - Цепочка: site → building → section (подъезд) → storey → unit (квартира) → space (комната) → furniture → storage → item.
   - Подъезд выгружается как `IfcBuilding` с CompositionType = PARTIAL, квартира — как `IfcSpace` с CompositionType = COMPLEX, объединяющий комнаты.
2. **Своя система координат у каждого уровня.**
   - `placement` = сдвиг + поворот вокруг Z относительно родителя.
   - Метры, ось Z вверх, правая система. Геометрия лежит в собственной системе сущности.
   - Участок привязан к Земле точкой `georef` (WGS84 и локальная ENU).
3. **Стабильные id.**
   - Импортированное получает `uuid5(пространство, key)`: пересборка даёт те же id, пакеты ссылаются друг на друга без поиска.
   - Ручное получает случайный UUID (позже UUIDv7).
   - IFC GlobalId выводится без потерь (`ifc_guid`, совпадает с `ifcopenshell.guid.compress`).
4. **Приватность у каждой сущности.**
   - Уровни public → residents → household → owner → secret, наследуются внутри пакета.
   - Выгрузки получают аудиторию. Пакеты разделены по владельцам.
5. **Федерация без сервера.** Пакет квартиры ссылается на этаж из пакета квартала по id. Владелец квартиры хранит свой пакет, пакет квартала ведёт его хозяин.
6. **Происхождение и точность.** Например, `src: {from: "project:OV-10a", acc: 0.5}`. Схематичное не выдаётся за точное.
7. **Внешние системы — через `bind`.** Например, `ha.entity`, `osm.way`, `dreame.segment`, `brti.room`. Ядро о них не знает, адаптеры живут в приложениях.
8. **Одна точка правды для схемы.** pydantic-модели → JSON Schema (`schema/`) → типы для других языков.

## Модель

| Поле | Смысл |
|---|---|
| `id`, `key` | UUID и человекочитаемый ключ |
| `kind`, `type` | Вид и подтип из словаря `schema/kinds.json` |
| `parent` | Вложение |
| `placement`, `geom` | Положение и геометрия: `extrusion`, `box`, `polyline`, `point`, `mesh` |
| `props` | Площади, артикулы, номиналы |
| `bind` | Связи с внешними системами |
| `refs` | `feeds`, `controls`, `has_member`, `stacked_above`… |
| `privacy`, `src`, `tags`, `aliases` | Видимость, происхождение, теги, синонимы для поиска и голоса |

## Стандарты (октябрь 2026)

| Стандарт | Состояние | Использование |
|---|---|---|
| IFC 4.3 (ISO 16739-1:2024) | Действует | Цель выгрузки. Сейчас пишем IFC4 (запасной вариант). Отличия 4.3: `IfcDistributionBoard`, `Pset_SpaceCommon.IsExternal` |
| IFC5 / IFCX | Альфа, основа не утверждена | Идеи без синтаксиса: дети по именам, атрибуты с пространствами имён, слои-наложения |
| GeoJSON, IMDF 1.0 | Стабильны | 2D-карты квартала и общих зон (MapLibre, Leaflet) |
| glTF 2.0 | Стабилен | 3D в браузере. IFC → GLB на сервере через IfcOpenShell |
| CityJSON 2.0 | OGC | Район: здания, `BuildingUnit` для квартир |
| Brick 1.4 | Стабилен | Подсказка класса у помещений и устройств |

Привязка района и IFC: `IfcMapConversion` в проекции UTM 35N (EPSG:32635) для Беларуси и соседей. Обычно — UTM своей зоны.

IfcOpenShell (LGPL) — необязательная зависимость. На Alpine он не ставится (нет колёс musllinux), поэтому выгрузку в контейнере делаем на Debian.

## Сервер (0.2)

`cherrybim.server` — один процесс на Starlette и uvicorn, экстра `server`. Им же собран аддон Home Assistant.

```
браузер (three.js) ──HTTP /api/*, WebSocket /api/live──┐
голосовой ассистент ──MCP /mcp (streamable HTTP)───────┤── Server ── Store ── *.twin.json (только чтение)
                                                       │                 └── items.twin.json, trash.jsonl
Home Assistant ◄── REST (службы), WebSocket (state_changed) ── HA
```

- **Пакеты** лежат в папке и только читаются; их пересобирают скриптом и подкладывают заново, сервер замечает новое время файла. **Вещи** — отдельный пакет `items.twin.json` в папке данных: его правят API и MCP, запись атомарная, вычеркнутое уходит строкой в `trash.jsonl`. Поправили файл руками — сервер перечитает его, а не затрёт.
- **Поиск** (`Twin.rank`): слово в названии и синонимах — 3 очка, в названиях родителей и того, на что ссылается сущность, — 2 («ящик 2 в спальне», «обои в спальне»), в тегах и свойствах — 1; найдены все слова — ещё 10. Однобуквенные слова необязательны: «в» — предлог, «секция б» — метка. Место для вещи выбирается только при полном совпадении, ничья — «уточни, какой именно».
- **MCP**: `find`, `contents`, `add_item`, `move_item`, `remove_item`, `show`, `documents`. Без сессий и с JSON-ответами: клиент HA открывает новую сессию на каждый вызов. Ответы — короткий русский текст с путём от комнаты, его можно читать вслух.
- **Живые состояния.** Сервер подписывается на `state_changed` и пересылает браузерам только привязанные сущности (`bind["ha.entity"]`). Пылесос: `bind["dreame.affine"]` — аффинное преобразование системы квартиры в миллиметры робота; по нему сервер ставит робота на 3D-план и шлёт `vacuum_goto` в точку, по которой щёлкнули.
- **Доступ.** Вход только с адресов из `--allow` (в аддоне — сеть Supervisor). Отсюда можно щёлкать лишь `light`, `switch`, `fan` из привязок; замков нет.
- **Просмотрщик** — статичные файлы (`static/`, three.js 0.170 и нужные модули `examples/jsm` лежат рядом), все адреса относительные, поэтому страница работает и под ingress. Виды «Квартира», «Дом», «Квартал»; срез стен на 1,15 м; выбранный шкаф и шкаф с выбранным ящиком полупрозрачны, повторный щелчок проваливается шкаф → секция → ящик; ящик показывается спереди (фасад мебели — сторона −Y её системы). Подробнее — ниже, «Реалистичная геометрия (0.4)».

### Реалистичная геометрия (0.4)

Форма — как у настоящей вещи, поверхности — без текстур: цвет, шероховатость, металл. Объём дают свет и тени, а не картинки.

- **Модели по типам** (`static/families.js`). Пакет хранит только габариты (`box`) или точку и тип; модель строится из них при загрузке. Например, `furniture.bed` — царга, матрас, одеяло, подушки и изголовье у стороны +Y; `opening.window` — рама, створки со стеклом и ручками, подоконник, стена под окном и над ним. Тип без своей модели рисуется прежней коробкой. Детали сливаются по материалам (`static/kit.js`): у сложной мебели несколько вызовов отрисовки.
- **Ориентация.** Фасад — сторона −Y системы сущности, как у мебели из OpenFurnitureMaker. У проёма X идёт вдоль стены, −Y — сторона комнаты, у двери — сторона, куда она открывается. Старые пакеты, где коробка проёма лежит поперёк стены, разворачиваются по контуру квартиры: снаружи — улица.
- **Подсказки отрисовки** — словарь `props.render`. Это не данные о вещи, поэтому их нет в карточке, в поиске и в ответах ассистента:
  - `colors` — цвета частей: `{"body": "#b39069", "front": "#75805c", "*": "#ffffff"}`;
  - у дверей `hinge` (`left`/`right` — где петли, если смотреть со стороны открывания), `open` (угол, градусы), у балконного блока `leaf` (ширина створки);
  - у мебели `handles` (`gola`, `bar`, `knob`, `none`), у шкафа `fronts` — двери `{"x": [x0, x1], "z": [z0, z1], "hinge": …, "handle": [x, z0, z1]}` и `fillers` (из проекта OFM: `io_ofm.facade_from_ofm`);
  - у места хранения `front` — что спереди: `drawer`, `door`, `open`, `shelf`, `hooks`, `none`;
  - у отделки `on` — куда ложится (`floor`, `walls`, `skirting`, `ceiling`): пол комнаты красится по ней, плинтус ставится вдоль стен;
  - у отопительного прибора `style` (`panel`, `convector`), у окна `sashes` (число створок) и `railing` (ограждение снаружи «французского» окна), у зеркала `frame`, `shelf`, `backlight`;
  - у мебели `legs` (`wood`, `casters`, `plinth`, `short`, у стола `panel`, `splay`, `trestle`; `false` — без ножек), у корпусной мебели `cells` — ячейки фасада `[u0, v0, u1, v1, вид, петли]` в долях ширины и высоты; у обеденного стола `table_w`, `table_l`, `chairs_per_side`, `chairs_at_ends`, `chair_out` (число или `{side, ends}`); у кухни `strips` (полосы между ярусами, `[z0, z1, часть, x0, x1]`), `counter` (`[x0, x1]` — столешница не на всю ширину, в углу её кладёт соседний модуль) и `backsplash` (`{top, x}`); у штор `panel` (ширина полотна или пара `[левое, правое]`); у двери шкафа `handle: false` — без ручки;

    - у роутера `style: "tower"` — узел Mesh башенкой без антенн: скруглённый корпус, решётка сверху, индикатор спереди внизу; `style: "wedge"` — длинный корпус трапецией и в сечении, и по длине (юбка из рёбер, узкий гребень с медной полосой, индикаторы, надпись и рамка NFC на передней грани), антенны-лопасти с остриями: `antennas` средних за гребнем (по умолчанию 5, места — по фото Xiaomi BE7000) и две по торцам; цвета `body`, `base`, `accent`;
    - у линии (`geom.type: "polyline"`) `exposed` — проложена открыто: кабель или труба из скрытых типов (`cable`, `pipe_pair`, …) видны и без режима «Инженерия»; `color` — цвет оболочки, иначе цвет по типу.
  - 0.5.2:
    - вещи из учёта (`kind: item`) с коробкой рисуются моделями по типу (`static/things.js`): `kettle`, `frying_pan`, `suitcase` (`ribs`: `"diagonal"` или `"horizontal"`, `rib_count`, `wheels` — высота колёс), `humidifier`, `stepladder` (сложена: `steps` — ступеней под площадкой, `platform` — её высота), `sewing_machine`, `hammer_drill` (`case: false` — без кейса); место вещи — в системе её родителя (комнаты, ящика), при переносе в другое место оно сбрасывается;
    - у розетки `lid` — откидные крышки на каждом месте рамки;
    - сантехнические выводы `mep.water_outlet` и `mep.drain_outlet` — точкой, наружу −Y, цвет `colors.cap`; короб `mep.pipe_box`;
    - у входной двери `lock: "push_pull"` — умный замок push-pull с панелями 77 × 406 мм по обе стороны полотна на 0,84–1,25 м, ручки-лопатки на 0,90–1,06; цвета `lock_frame`, `lock_body`, `lock_handle`. Устройство `smart_lock` само ничего не рисует: только объём для выбора.
  - Тот же выпуск, без подсказок:
    - у плинтуса по контуру комнаты — уголки в углах и заглушки у дверей; где стена кончается не дверью, плинтус заворачивает на её торец наружным уголком;
    - у базы пылесоса робот в доке рисуется своим материалом с меткой `dock`. Пока живой робот (поза с карты) не в доке, просмотрщик этого робота прячет.
  - у светильника `fixture` (`grid`, `rays`, `ring`, `disc`, иначе плафон), `angle` — поворот от осей комнаты, `diameter` — длина планок решётки, размах лучей или диаметр диска и колец. Светильник с `placement`, но без коробки, висит в этой точке, иначе — в центре комнаты.
- **Буфер глубины.** В виде квартиры ближняя и дальняя плоскости камеры 0,05 и 300 м (в виде дома и квартала — 0,3 и 5000): иначе за тонкой стеной проступает силуэт вещи из соседней комнаты. Издалека ближняя плоскость отодвигается — на 0,04 расстояния от камеры до цели: точность буфера падает как квадрат расстояния, делённый на ближнюю плоскость, и с облёта в 25 м при 0,05 шаг был больше миллиметра — фасады с подложкой в миллиметре за ними мерцали. Режиссёр, когда камера проходит вплотную к мебели, ограничивает её сверху (`camera.userData.nearCap`: 0,6 расстояния до ближайшей детали), чтобы она не резала вещь. Грани разных вещей строго в одной плоскости (порог на уровне пола, шкафчик узла заподлицо со стеной, дверца в корпусе) после сборки сцены получают ранг (`coplanar.js`): меньшая вещь — деталь на основе — рисуется ближе на 10⁻⁵ расстояния за ранг; это масштаб вида с центром в камере, на экране ничего не сдвигается, а спор «кто ближе» всегда решён в одну сторону. `?msaa=0` выключает сглаживание в буфере кадра: программный WebGL (SwiftShader) пропускает в MSAA-буфере кромки закрытых вещей; сверочные рендеры поэтому идут без MSAA с двойной плотностью пикселей и уменьшаются. Плотность пикселей просмотрщик берёт один раз, при загрузке страницы, поэтому её задают до открытия: иначе холст 1× просто растягивается.
- **Свет.** Окружение комнаты из примитивов three.js (`RoomEnvironment`) для отражений, солнце с мягкими тенями, затенение углов GTAO, нейтральный тонмаппинг. Под потолком (вид квартиры без среза) солнца нет: свет рассеянный, небо и окружение ярче (`INSIDE_LIGHT`, подбор — `?lt=`). Солнце сверху в комнате с потолком засвечивало пол и рисовало на стенах тени, которых в комнате при лампах нет; по 15 фото хозяев так ближе к снимкам. Из окон в этом виде видно окружение: дома и двор пакета квартала (у домов окружения `type: "context"` — по карте, без окон и подписей) и ровная земля; свой дом скрыт. Небо там — по высоте солнца из `sun.sun` HA: день, сумерки, ночь (`?sky=` — вручную). Холст прозрачный: фон — цвет темы страницы; цвета в буфере умножены на альфу, и перед тонмаппингом умножение снимается, иначе стекло поверх фона светлеет ореолом.
- **Срез.** Стены — призмы, их срез — масштаб по Z. У проёмов (рамы, створки, полотна) две сборки, целая и обрезанная на 1,15 м.
- **Потолок.** В виде квартиры без среза у комнат есть потолок на высоте потолка квартиры. Он виден только снизу, поэтому сверху на квартиру не мешает. Стены и проёмы в этом виде не отбрасывают тень от «солнца» внутрь комнат: в настоящей комнате свет рассеянный.
- **Стыки и щели.** Грань стены, которая упирается в соседнюю стену или в коробку двери, не строится. Иначе её ребро лежит в плоскости лицевой грани соседа, бьётся с ней по глубине и рисует на стене светлый пунктир. Куски стены в проёмах (перемычка, стена под окном, коробка двери) утоплены на 0,5 мм, наличник отстоит от стены на 1 мм, пол в проёме на 0,5 мм ниже пола комнат и заходит под него — по той же причине. В щель у косяка видна «заглушка» внутри стены. Двусторонние материалы для этого не годятся: обратная сторона соседней грани выигрывает на ребре и рисует тот же пунктир. В щели между фасадами мебели и дверями шкафов — подложка цвета фасада ×0,6 (в просветах вешалки из реек — ×0,8): щель видна тонкой линией тона фасада, а не чёрной. У наружных кромок ряда фасадов подложки нет — там видна кромка корпуса; у кромки, к которой вплотную примыкает панель (`abut`), она есть. Узкий промежуток между ящиками стола закрыт такой же подложкой. В сверочных рендерах без MSAA щели тоньше пикселя рвутся в пунктир; с MSAA, как в просмотрщике по умолчанию, они сплошные.
- **Профиль gola.** Над фасадом — канал 3 см (L-профиль под столешницей), между двумя фасадами одной колонки — средний С-профиль 2 см. Навесной модуль с `underside` начинается над панелью дна: иначе их грани совпадают и по нижней кромке антресолей идёт «пила».
- **Плинтус** обходит стены комнаты и кончается у наличника двери, а не у проёма; в проходе без двери идёт по обоим откосам.
- **Скрытое и состояние.** Трубы и кабели в стенах и стяжке видны в режиме «Инженерия» рентгеном: копия меша рисуется только там, где её закрывают. Устройство без места в комнате — маленький индикатор; у светильника — светильник своего вида у потолка (тени не отбрасывает), на срезе — тонкое кольцо на полу под ним, включённый свет — пятно на полу комнаты.
- **Экраны.** Выключенный экран ТВ и станции тёмный — и без Home Assistant; включённый красится по состоянию.
- **Встроенная техника.** Колонны и навесные шкафы — сплошной корпус, поэтому духовка, микроволновка и подобная техника ставятся фасадом в плоскость корпуса: их стекло выступает вперёд, как у настоящей встройки, и не мерцает вместе с гранью корпуса.
- **Нагрузка.** Квартира на 200 сущностей — около 400 мешей, 1,5 тыс. вызовов и 220 тыс. треугольников за кадр вместе с тенью и затенением углов. Кадр рисуется только при изменениях; если он стабильно дольше 30 мс, просмотрщик отключает затенение углов, потом снижает плотность пикселей.
- **Честность.** Модель не выдумывает того, чего нет в данных: окна на фасадах домов не рисуются (их положение неизвестно), устройство без координат не ставится в угол комнаты как настоящее.

### Мебель из БАЗИС-Мебельщика (0.5)

Корпусную мебель на заказ проектируют в БАЗИС-Мебельщике: в модели `.b3d` каждая панель с вырезами, фурнитура, присадка. Такая мебель рисуется не по типу, а по своим деталям.

- **Выгрузка** — скрипт `tools/bazis/cherrybim-export.js`, запускается из меню «Скрипты» БАЗИС-Мебельщика (11.6, API 1101). Скрипт лежит в `Документы\Bazis11\Scripts\` в cp1251, рядом `cherrybim-export.json`: `{"files": [...], "out": "папка"}`. Каждый файл грузится в свой блок (`AddBlock` + `Load`) и выгружается в `<out>/<имя>.json` (БАЗИС пишет его в cp1251). Без списка выгружается открытая модель с запросом имени файла. У панели — материал, толщина, контур в её системе (отрезки, дуги, окружности), начало `o` и оси `ex`, `ey`, `ez` в глобальной, габарит; у сборки — `AnimType` и `FurnType` (фурнитура: петля, направляющая, навеска); отверстия — объекты с именем-диаметром («4»). Флаг `IsFastener` в этом API не булев — проверять `=== true`.
- **Импорт** — `cherrybim.io_bazis.Model(load(json), pick=None, lift=0)`. Оси БАЗИСа: X — ширина, Y — высота, Z — глубина, фасад в +Z; переводятся в систему мебели Cherry BiM (X вдоль фасада, Y от фасада вглубь, Z вверх) поворотом, без зеркала. `pick` — оставить часть файла (два изделия в одном), `lift` — высота опор, которых нет в проекте.
  - Роли панелей: `back` — ХДФ/ДВП по материалу; `front` — фронтальная панель, лицо которой не дальше 3 мм от переднего края мебели (двери, фасады ящиков, фриз, планки); остальное — `body`. Внутренние фасады ящиков за дверью — корпус.
  - Двери — фасады с петлями: сторона петель по их центрам (`hinge`: left, right, top, bottom). Ящики — по направляющим: короб — панели над направляющей между её концами, фасад — лицевая панель перед ней (бывает шире корпуса).
  - Ручки — по отверстиям на фасаде: две-три точки на одной прямой дают ось, середину и межосевое; длину, ширину и вылет скобы задаёт таблица `{межосевое мм: (длина, ширина, вылет)}`, иначе межосевое + 28 мм.
  - Ячейки корпуса — гильотиной по проекции на фасад: сквозная стойка делит прямоугольник на колонки, сквозная полка — на ярусы, пока делить нечем. Короба ящиков, фасады и задние стенки в разбиении не участвуют, учитываются панели глубиной от половины корпуса. Глубина ячейки — от передних кромок окружающих стоек и полок до ближайшей стенки за ней.
  - `storage_from_bazis(m, мебель, ns, sections, names, hanging)` — места хранения: ячейки (`c1…` снизу вверх, `hanging` — штанга) и ящики (`d1…` сверху вниз) по секциям, заданным прямоугольниками, или прямо в мебели. Названия и синонимы можно переопределить по ключу.
- **Отрисовка** — `props.render.parts`: коробка `{"b": [x0, y0, z0, x1, y1, z1]}`, контур `{"p": [[u, v], …], "ax": ось толщины, "d": [от, до], "h": вырезы}` (точки при ax "x" — (y, z), "y" — (x, z), "z" — (x, y)) или цилиндр `{"cyl": [x, y, z0, z1, r]}` (опоры); `m` — роль и ключ цвета в `colors` (`body`, `front`, `back`, `legs`…). `handles_at` — ручки: концы `x`, `z`, лицо фасада `y`, крепления `posts`, ширина `w`, вылет `d`. Места хранения внутри такой мебели не рисуют ничего, кроме штанги (`rod_drop` — от верха ячейки, по умолчанию 0,06).
- Материалы в файлах конструктора бывают не обновлены (декор меняют в сводном файле для заказа) — верные в счетах на распил: размеры деталей там по декорам.

### Документы у сущностей

У любой сущности — своя база документов: инструкции, проект и чертежи, чеки, гарантии, договоры, страницы магазина.

- **Документ** — сущность вида `document` (`docs.py`, IFC — `IfcDocumentReference`). Родитель — то, к чему он относится (холодильник, кухня, шкаф). Если документ описывает и другие вещи, у него связи `documents` (проект кухни → все её модули). Подтипы: `project` (проект, чертежи), `assembly` (инструкция по сборке, монтажу), `manual`, `datasheet`, `receipt`, `warranty`, `contract`, `page` (страница сайта), `photo`, `note`.
- **Ссылка и копия.** `props.url` — где документ в сети; `props.file` — локальная копия, путь от корня папки документов (`--docs`, по умолчанию `DATA/docs`); ещё `mime`, `size`, `pages`, `sha256`, `saved_at`. Копия открывается, даже если сайт пропал или переделан. Пакет хранит только путь, файлы лежат рядом с пакетами и в git не нужны.
- **Где видно.** В карточке — «Документы»: свои и документы ближайшего родителя на всё целое (`project`, `assembly`, `contract`): у ящика кухни — проект кухни, а чек на розетку кухни — только у розетки. Наследуют части, а не вещи, которые там лежат: у телефона в ящике проекта кухни нет. Документ, который уже есть в своих (проект кухни связан с её модулями), второй раз «у родителя» не повторяется. Карточка документа: открыть копию, скачать, на сайт, к чему относится; кнопки копии — только если сервер нашёл файл в папке документов (`copy` в снимке). Видно и считается (`find`: «документов: N») только то, что открыто аудитории; закрытое не находится и по id.
- **Добавить из просмотрщика**: файлом (`POST /api/docs?to=…&title=…&type=…&filename=…`, тело — файл до 50 МБ; `filename` обязателен, поэтому файл `.json` не путается с запросом) или ссылкой (`POST /api/docs` с JSON `{to, title, type, url, copy}`): при `copy` сервер скачивает копию сам — PDF и картинки как есть, страницу HTML-копией с `<base href>`, переведённой в UTF-8 из её кодировки. Тип копии — по содержимому, а не по адресу: PDF со страницы `download.php` ляжет как `.pdf`. Такие документы пишутся в пакет вещей, убираются в `trash.jsonl`; вычеркнули вещь — её документы уходят в ту же строку корзины. `GET /api/doc/{id}` отдаёт копию с адреса просмотрщика, а под ingress это адрес самого HA, поэтому из копии ничего не выполняется: PDF, картинки и текст открываются во вкладке, страница и SVG — в песочнице (`Content-Security-Policy: sandbox`), остальное (XML, офисные файлы, неизвестное) — только скачать. Путь копии не выходит за папку документов.
- **Копии страниц при сборке пакетов**: `python -m cherrybim.docs snapshot URL файл.pdf` — Chrome без окна по протоколу отладки печатает экранную вёрстку в PDF с текстом, предварительно убрав всплывающие окна и затемнение. Печатную вёрстку магазины часто прячут целиком, поэтому `--print-to-pdf` давал пустую страницу. `fetch` — скачать файл как есть.
- **Закрытые номера** (IMEI, серийный номер, MAC) — словарь `props.ids` у самой вещи. Его нет в поиске (индексируются только строковые свойства) и в ответах ассистента; в карточке номер скрыт (видны последние 4 знака у длинного, 2 — у серийного из 8–11, короткий — целиком), «показать» — по кнопке, второй щелчок копирует. У вещей из пакета вещей номера правятся в «Изменить»: строка «название: номер», второй IMEI сохраняется как «IMEI 2»; название до 40 знаков, номер до 120.
- **Голос.** MCP-инструмент `documents(what)`: «какие документы, инструкции, чертежи есть у …» — названия, типы, есть ли копия, ссылки. `find` сообщает, сколько у сущности документов.

- **План картинкой** (`plan.py`, 0.3). Pillow, рисуется вдвое крупнее и уменьшается. Вместилище — квартира места, иначе этаж, иначе квартал. Рисуются только видимые аудитории сущности, мебель внутри мебели сверху пропускается. На экран план попадает так: сервер кладёт PNG в медиа HA и зовёт скрипт `--show-script`. Что дальше делает скрипт (например, ставит запрос в очередь ТВ), ядро не знает.

### Режиссёр показа (`director.js`)

Камера, которая сама ведёт зрителя: облёт квартиры, перелёт в комнату, полёт над трубами на высоте глаз, подход к вещи. Для экрана без мыши (телевизор, голос) и для экскурсий.

- **Планы.** Кадр — функция времени `pose(t) → {p, q, fov, roll}` (камера, точка взгляда, угол зрения, крен):
  - `Orbit` — облёт по кругу (`w`, рад/с) или качание `±sway` вокруг цели, наклон «дышит» `±breathe`; квартира облетается за 140 с;
  - `Glide` — полёт по пути с заранее рассчитанным профилем скорости;
  - `Still` — неподвижная поза.
- **Переход** (`Blend`) — оптимальный перелёт «панорама + наезд» (van Wijk, Nuij, 2003; как `d3.interpolateZoom`): цель едет по прямой, расстояние до неё меняется так, что картинка бежит перед глазами с постоянной скоростью, — на дальнем перелёте камера сама отъезжает и поднимается над квартирой, потом подходит. Азимут — по кратчайшему углу, наклон — плавно, на дальнем перелёте (по сравнению с расстоянием до цели) ещё приподнимается до +16°. Вес — кривая минимального рывка `u³(10 − 15u + 6u²)`: скорость и ускорение на краях нулевые; у долгих переходов — гладкая трапеция: разгон и торможение той же кривой, посередине ровная скорость (пик — 1/(1 − ρ) от средней вместо 1,875). Оба плана внутри перехода продолжают двигаться, поэтому начатый облёт не обрывается; полёт по трассе трогается за 1,6 с до конца перехода.
- **Длительность перехода** (`fitT`) — проигрышем: переход заранее считается по 90 точкам и растягивается, пока видимая скорость не уложится в 0,5 расстояния до цели в секунду (движение прямо на цель весит в √2 раз меньше бокового — наезд глаз переносит легче), ускорение — в 0,45 расстояния в с², поворот взгляда — в 30°/с, наезд объективом — в 7°/с. Начальная — от пути цели, поворота и смены расстояния (1,9–5,4 с), верх — 20 с. Скорости в переходе ~1/T, ускорение ~1/T², поэтому T растягивается на худшее превышение (по ускорению — на корень).
- **Кадрирование** — точное для перспективы: углы коробки в базисе камеры, расстояние — наименьшее, при котором все углы в кадре с полями. Облёт квартиры проверяется на всём круге через 10°: квартира в кадре при любом азимуте. Комната — со стороны середины квартиры, на три четверти, сверху 56°; вещь — спереди (фасад −Y её или её держателя) на три четверти, низкая — сверху круче, висящая высоко — почти в лоб; мелочь — с запасом вокруг, чтобы было понятно, где она.
- **Пролёт по трассе** (`route`): полилинии системы (её `has_member`) сливаются в граф узлов; концы трасс посреди чужих отрезков — тройники. Начало — узел, который питает остальных (`feeds`, узел ввода), иначе конец самой длинной трассы. Ноги облёта — обход графа: ветки короче 1,6 м видны по пути, несколько длинных из одного тройника — по очереди, самая длинная последней. Путь ноги — углы скруглены дугами (`smoothPath`, до 0,65 м), затем путь пересэмплирован через 2 см и сглажен (±12 см, три прохода): кривизна на входе в дугу нарастает плавно, как на переходной кривой дороги, и боковое ускорение включается без толчка. Профиль скорости (`speedProfile`) — до 0,9 м/с, в поворотах по боковому ускорению (0,35 м/с²) и скорости разворота (0,62 рад/с), у приборов медленнее, и везде так, чтобы взгляд разворачивался не быстрее ~29°/с (`gazeCap`: шпилька трубы, разворот к прибору); разгон и торможение не резче 0,5 м/с², трогание и остановка — с рывком не больше 0,8 м/с³; внутри шага профиля движение равноускоренное — скорость без ступенек.
  - Камера — на высоте 1,5 м над полом, но **сбоку от трубы** (`lateral`): туда, где до стены комнаты дальше, не больше 0,95 м и не дальше половины свободного места, со сглаживанием вдоль пути. Трубы идут вдоль стен и под окнами — камера над самой трубой скребла бы стену и пролетала сквозь шторы. Над стеной между комнатами камера приподнимается на 0,6 м.
  - Взгляд — на среднее пяти точек впереди (0,55–1,45 от 2,4 м; за концом пути — дальше по последнему направлению): на поворотах он разворачивается заранее и плавно. К приборам по пути голова поворачивается по плавным весам (несколько рядом — взгляд между ними; «ближайший прибор» сменялся бы скачком), к концу ноги взгляд съезжает на прибор в конце, к узлу ввода в начале ноги не оборачивается. Крен в поворотах — до 2,5°, считается заранее по всему пути и сглажен вдоль него; боковой сдвиг и подъём между отсчётами — сплайном Катмулла — Рома.
  - Сцена отопления: общий план с титром и мини-планом → узел ввода вплотную → ноги полёта (полосы кино), у каждой — план на прибор в конце с титром → общий план. По трубам бегут штрихи: подача тёплая — от узла, обратка синяя — к узлу; трубы в стяжке видны рентгеном.
- **Загораживание.** Мебель и техника, в которые въезжает камера, исчезают, а то, что между камерой и целью, становится полупрозрачным. Проверка — лучами к цели (у вещи — ещё к её верху и верхним углам) по коробкам, а для попавших в коробку — по самой геометрии раз в 4 кадра (у кровати коробка выше матраса, а луч идёт над ним). Подмена материалов — только на время кадра (`beforeRender`/`afterRender`): просмотрщик ничего не теряет.
- **Выбор.** Комната — свой свет: тёплый пол, светящийся контур по низу стен и световая завеса, гаснущая к срезу. Вещь — тёплое пульсирующее свечение поверх её настоящих цветов. Ящик или вещь в шкафу — выбор просмотрщика (шкаф становится прозрачным).
- **Поверх кадра** — свой 2D-холст (`Overlay`): титр внизу слева (заголовок и подпись), подписи у вещей с выноской, мини-план в углу (комнаты, трасса, камера с конусом взгляда), полосы кино, виньетка, затемнение. В браузере — слоем над сценой, в потоке — склейкой с кадром.
- **Часы.** `tick(now)` — время страницы или потока; планы и сцены живут по своему времени, которое стоит на паузе.
- **Пересборка сцены** (новые данные с сервера) показ не перезапускает: планы и пути те же, заново — подсветка и выбор, которые просмотрщик сбросил вместе со сценой (`onRebuild`).
- **Команды** — `director.play({op, id, ids, title})`: `overview`, `room`, `object`, `route`, `group`, `tour` (все комнаты по кругу, от прихожей), `auto` (вид по сути сущности: квартира — облёт, комната — комната, система или труба — трасса, отделка — комнаты с ней, остальное — вещь), `key` (◀ ▶ — соседняя комната, ▲ ▼ — ближе и дальше, ОК — пауза), `stop`. Ответ — `{ok, op, title, sub, seconds}` для голосового ответа.
- **Режим `?tv=1`** — экран без панелей и указателя, тёмный фон, камеру ведёт режиссёр, плотность пикселей 1; `?ss=2` — кадр вдвое крупнее, поток ужимает его ровно вдвое (с MSAA ×4 — 16 выборок на точку: тонкие кромки и блики издалека не мерцают). `?autoplay=1` — сразу облёт.
- **Поток** (`capture.js`): кадр сцены и подписи склеиваются в холст, WebCodecs кодирует его H.264 (видеокарта, `latencyMode: realtime`, Annex B), куски уходят по WebSocket. Кадров ровно `fps` в секунду реального времени, сцена живёт по номеру кадра; не успел — следующие кадры рисуются без пауз, пока не догонят время (у телевизора запас 1,6 с), и только при отставании больше 1,2 с номер перескакивает (это прыжок камеры); занятый кодировщик ждут, кадр не выбрасывают. Размер потока — экранный размер холста. `snapshot(t)` — один кадр, как его увидит экран. Что делать с кусками (HLS для телевизора), ядро не знает.
