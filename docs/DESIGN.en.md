# Cherry BiM: architecture

Format version 0.1. This document explains the decisions that are expensive to change later and how the format relates to standards.

## Purpose

One model for every scale of housing and every consumer:

- a Home Assistant module with a 3D plan and item inventory;
- a residents' bot with a map of the block;
- a voice assistant via MCP;
- exports to BIM and GIS software.

This is not a BIM editor. It is compact JSON with exports to standards.

The format has been tested on a real apartment and block (the data itself is not published):

- 174 entities in two packages;
- a cabinet from OpenFurnitureMaker broken down into sections, 9 drawers and compartments;
- after georeferencing, the apartment's facade matched the building outline to within hundredths of a degree;
- the IFC4 export passes IfcOpenShell schema validation with no errors.

## Decisions

1. **A nesting tree as in IFC.**
   - Chain: site → building → section (entrance) → storey → unit (apartment) → space (room) → furniture → storage → item.
   - An entrance is exported as `IfcBuilding` with CompositionType = PARTIAL, an apartment as `IfcSpace` with CompositionType = COMPLEX, grouping the rooms.
2. **Each level has its own coordinate system.**
   - `placement` = translation + rotation about Z relative to the parent.
   - Metres, Z axis up, right-handed. Geometry lives in the entity's own coordinate system.
   - The site is tied to the Earth by a `georef` point (WGS84 and local ENU).
3. **Stable ids.**
   - Imported entities get `uuid5(namespace, key)`: a rebuild yields the same ids, and packages reference each other without lookups.
   - Manually created ones get a random UUID (later UUIDv7).
   - The IFC GlobalId is derived losslessly (`ifc_guid`, identical to `ifcopenshell.guid.compress`).
4. **Privacy on every entity.**
   - Levels public → residents → household → owner → secret, inherited within a package.
   - Exports are made for an audience. Packages are split by owner.
5. **Federation without a server.** The apartment package references a storey from the block package by id. The apartment owner keeps their package; the block package is maintained by its own owner.
6. **Provenance and accuracy.** For example, `src: {from: "project:OV-10a", acc: 0.5}`. Schematic data is never passed off as precise.
7. **External systems go through `bind`.** For example, `ha.entity`, `osm.way`, `dreame.segment`, `brti.room`. The core knows nothing about them; adapters live in the applications.
8. **A single source of truth for the schema.** pydantic models → JSON Schema (`schema/`) → types for other languages.

## Model

| Field | Meaning |
|---|---|
| `id`, `key` | UUID and human-readable key |
| `kind`, `type` | Kind and subtype from the `schema/kinds.json` dictionary |
| `parent` | Nesting |
| `placement`, `geom` | Position and geometry: `extrusion`, `box`, `polyline`, `point`, `mesh` |
| `props` | Areas, article numbers, ratings |
| `bind` | Links to external systems |
| `refs` | `feeds`, `controls`, `has_member`, `stacked_above`… |
| `privacy`, `src`, `tags`, `aliases` | Visibility, provenance, tags, aliases for search and voice |

## Standards (October 2026)

| Standard | Status | Use |
|---|---|---|
| IFC 4.3 (ISO 16739-1:2024) | In force | Export target. We currently write IFC4 (fallback). Differences in 4.3: `IfcDistributionBoard`, `Pset_SpaceCommon.IsExternal` |
| IFC5 / IFCX | Alpha, foundation not approved | Ideas without the syntax: children by name, namespaced attributes, overlay layers |
| GeoJSON, IMDF 1.0 | Stable | 2D maps of the block and common areas (MapLibre, Leaflet) |
| glTF 2.0 | Stable | 3D in the browser. IFC → GLB on the server via IfcOpenShell |
| CityJSON 2.0 | OGC | Neighbourhood: buildings, `BuildingUnit` for apartments |
| Brick 1.4 | Stable | Class hint for spaces and devices |

Georeferencing of the neighbourhood and IFC: `IfcMapConversion` in the UTM 35N projection (EPSG:32635) for Belarus and its neighbours. In general, the UTM zone of the location.

IfcOpenShell (LGPL) is an optional dependency. It does not install on Alpine (there are no musllinux wheels), so we run exports in a container on Debian.

## Server (0.2)

`cherrybim.server` is a single process on Starlette and uvicorn, the `server` extra. The Home Assistant add-on is built from it too.

```
браузер (three.js) ──HTTP /api/*, WebSocket /api/live──┐
голосовой ассистент ──MCP /mcp (streamable HTTP)───────┤── Server ── Store ── *.twin.json (только чтение)
                                                       │                 ├── items.twin.json, trash.jsonl
                                                       │                 ├── ideas/*.idea.json, state.json
                                                       │                 └── assets/*.glb (готовые модели)
Home Assistant ◄── REST (службы), WebSocket (state_changed) ── HA
```

- **Packages** sit in a folder and are read-only; they are rebuilt by a script and dropped in again, and the server notices the new file time. **Items** are a separate package, `items.twin.json`, in the data folder: the API and MCP edit it, writes are atomic, and a crossed-out item goes as a line into `trash.jsonl`. If you edit the file by hand, the server rereads it rather than overwriting it.
- **Search** (`Twin.rank`): a word in the name and aliases scores 3 points; in the names of parents and of what the entity references, 2 ("drawer 2 in the bedroom", "wallpaper in the bedroom"); in tags and properties, 1; all words found adds another 10. One-letter words are optional: «в» ("in") is a preposition, «секция б» ("section B") is a label. A location for an item is chosen only on a full match; a tie gives "specify which one".
- **MCP**: `find`, `contents`, `add_item`, `move_item`, `remove_item`, `show`, `documents`. No sessions and JSON responses: the HA client opens a new session for each call. Responses are short Russian text with the path from the room, suitable for reading aloud.
- **Live states.** The server subscribes to `state_changed` and forwards to browsers only bound entities (`bind["ha.entity"]`). Vacuum: `bind["dreame.affine"]` is an affine transform from the apartment coordinate system to the robot's millimetres; with it the server places the robot on the 3D plan and sends `vacuum_goto` to the clicked point.
- **Access.** Requests are accepted only from addresses in `--allow` (in the add-on, the Supervisor network). From here you can toggle only `light`, `switch` and `fan` from the bindings; no locks.
- **Viewer**: static files (`static/`, with three.js 0.170 and the needed `examples/jsm` modules alongside), all URLs relative, so the page also works under ingress. Views Apartment («Квартира»), Building («Дом») and Block («Квартал»); walls cut at 1.15 m; the selected cabinet and a cabinet with a selected drawer become semi-transparent, and repeated clicks drill down cabinet → section → drawer; the invisible volume of a place does not hide what is visible behind it unless that belongs to the place (an organizer on a pegboard above the top of a shelving unit); a drawer is shown from the front (a piece of furniture's front is the −Y side of its coordinate system), and the camera goes to the nearest furniture (an organizer's drawer on a pegboard: to the organizer, not the pegboard). More below, in "Realistic geometry (0.4)".

### Realistic geometry (0.4)

Shapes are like the real thing; surfaces have no textures: colour, roughness, metalness. Volume comes from lighting and shadows, not images.

- **Per-type models** (`static/families.js`). A package stores only the dimensions (`box`) or a point and the type; the model is built from them on load. For example, `furniture.bed` is a frame rail, mattress, duvet, pillows and a headboard on the +Y side; `opening.window` is a frame, sashes with glass and handles, a sill, and the wall below and above the window. A type without its own model is drawn as the old box. Parts are merged by material (`static/kit.js`): complex furniture takes a few draw calls.
- **Orientation.** The front is the −Y side of the entity's coordinate system, as with OpenFurnitureMaker furniture. For an opening, X runs along the wall and −Y is the room side; for a door, the side it opens towards. Old packages where an opening's box lies across the wall are turned using the apartment outline: outside is the street.

- **Depth buffer.** In the apartment view the camera's near and far planes are 0.05 and 300 m (0.3 and 5000 in the building and block views): otherwise the silhouette of an item from the next room shows through a thin wall. From far away the near plane is pushed out to 0.04 of the camera-to-target distance: buffer precision drops as the square of the distance divided by the near plane, and in a 25 m orbit with 0.05 the step was over a millimetre, so fronts with a backing a millimetre behind them flickered. When the camera passes close to furniture, the director caps the near plane from above (`camera.userData.nearCap`: 0.6 of the distance to the nearest part) so that it does not clip the item. Faces of different items lying exactly in one plane (a threshold at floor level, a manifold cabinet flush with the wall, a door in a carcass) get a rank after the scene is built (`coplanar.js`): the smaller item, a part on a base, is drawn closer by 10⁻⁵ of the distance per rank; this is a view-space scale centred on the camera, nothing moves on screen, and the "which is closer" contest is always settled one way. `?msaa=0` turns off antialiasing in the framebuffer: software WebGL (SwiftShader) drops the edges of occluded items in an MSAA buffer; reference renders therefore run without MSAA at double pixel density and are downscaled. The viewer reads the pixel density once, on page load, so it has to be set before opening; otherwise a 1× canvas is simply stretched.
- **Lighting.** A room environment from three.js primitives (`RoomEnvironment`) for reflections, a sun with soft shadows, GTAO ambient occlusion, neutral tone mapping. Under the ceiling (apartment view without the cutaway) there is no sun: the light is diffuse and the sky and environment are brighter (`INSIDE_LIGHT`, tuned with `?lt=`). A sun from above in a room with a ceiling blew out the floor and cast shadows on the walls that a lamp-lit room does not have; judging by 15 of the owners' photos, this is closer to the pictures. In this view the surroundings are visible from the windows: the buildings and yard from the block package (surrounding buildings have `type: "context"`: from the map, without windows or labels) and flat ground; the apartment's own building is hidden. The sky there follows the sun elevation from HA's `sun.sun`: day, dusk, night (`?sky=` to set it manually). The canvas is transparent: the background is the page theme colour; colours in the buffer are premultiplied by alpha, and the premultiplication is undone before tone mapping, otherwise glass over the background lightens into a halo.
- **Cutaway.** Walls are prisms, and cutting them is a scale along Z. Openings (frames, sashes, leaves) have two builds: whole and cut at 1.15 m.
- **Ceiling.** In the apartment view without the cutaway, rooms have a ceiling at the apartment's ceiling height. It is visible only from below, so it does not get in the way when looking at the apartment from above. Ceiling-mounted light shades are not visible from above either (0.6): with the camera above the ceiling the fixture is hidden, otherwise it covers the room. With the camera below the ceiling (inside view) room labels are hidden: the neighbouring room's label would float over this one. In this view, walls and openings do not cast "sun" shadows into the rooms: in a real room the light is diffuse.
- **Joints and gaps.** A wall face that butts against a neighbouring wall or a door frame is not built. Otherwise its edge lies in the plane of the neighbour's front face, z-fights with it and draws a light dashed line on the wall. Wall pieces in openings (lintel, wall below the window, door frame) are recessed by 0.5 mm, the casing stands 1 mm off the wall, and the floor in an opening is 0.5 mm below the room floor and runs under it, for the same reason. The gap at the jamb shows a "plug" inside the wall. Double-sided materials do not work for this: the back side of the neighbouring face wins at the edge and draws the same dashed line. In the gaps between furniture fronts and cabinet doors there is a backing in the front colour ×0.6 (in the openings of a slatted coat rack, ×0.8): the gap shows as a thin line in the front's tone, not black. At the outer edges of a row of fronts there is no backing, and the carcass edge shows; at an edge that a panel butts against (`abut`), there is one. The narrow gap between table drawers is covered with the same backing. In reference renders without MSAA, gaps thinner than a pixel break into dashes; with MSAA, as in the viewer by default, they are continuous.
- **Gola profile.** Above a front there is a 3 cm channel (an L-profile under the worktop); between two fronts of one column, a 2 cm middle C-profile. A wall-hung module with `underside` starts above the bottom panel: otherwise their faces coincide and a "saw" runs along the lower edge of the top cabinets.
- **Skirting board** runs around the room walls and ends at the door casing, not at the opening; in a doorless passage it runs along both reveals.
- **Hidden things and state.** Pipes and cables in walls and screed are visible in the Building services («Инженерия») mode as an X-ray: a copy of the mesh is drawn only where it is occluded. A device with no position in the room is a small indicator; a light fixture is a fixture of its own kind at the ceiling (casting no shadows); in the cutaway, a thin ring on the floor below it; a light that is on is a spot on the room floor.
- **Screens.** A TV or station screen that is off is dark, even without Home Assistant; one that is on is coloured by its state.
- **Built-in appliances.** Tall units and wall cabinets are a solid carcass, so the oven, microwave and similar appliances are set with their front in the carcass plane: their glass protrudes, as in a real built-in, and does not flicker with the carcass face.
- **Load.** An apartment of 200 entities is about 400 meshes, 1.5 thousand draw calls and 220 thousand triangles per frame, including shadows and ambient occlusion. A frame is drawn only on changes; if it consistently takes longer than 30 ms, the viewer turns off ambient occlusion and then lowers the pixel density.
- **Honesty.** The model does not invent what is not in the data: windows on building facades are not drawn (their positions are unknown), and a device without coordinates is not put in a room corner as if it were real.

### Furniture from BAZIS-Mebelshchik (0.5)

Custom cabinet furniture is designed in BAZIS-Mebelshchik: a `.b3d` model holds every panel with cutouts, the hardware and the drilling. Such furniture is drawn not by type but from its own parts.

- **Export**: the script `tools/bazis/cherrybim-export.js`, run from the Scripts («Скрипты») menu of BAZIS-Mebelshchik (11.6, API 1101). The script lives in `Документы\Bazis11\Scripts\` in cp1251, next to `cherrybim-export.json`: `{"files": [...], "out": "папка"}`. Each file is loaded into its own block (`AddBlock` + `Load`) and exported to `<out>/<имя>.json` (BAZIS writes it in cp1251). Without a list, the open model is exported with a prompt for the file name. A panel has its material, thickness, outline in its own coordinate system (segments, arcs, circles), origin `o` and axes `ex`, `ey`, `ez` in the global system, and bounding box; an assembly has `AnimType` and `FurnType` (hardware: hinge, runner, hanger); holes are objects named by their diameter ("4"). The `IsFastener` flag is not a boolean in this API: check it with `=== true`.
- **Import**: `cherrybim.io_bazis.Model(load(json), pick=None, lift=0)`. BAZIS axes: X is width, Y is height, Z is depth, front at +Z; they are converted to the Cherry BiM furniture system (X along the front, Y from the front inwards, Z up) by a rotation, without mirroring. `pick` keeps part of the file (two products in one), `lift` is the height of supports missing from the project.
  - Panel roles: `back` is HDF/hardboard by material; `front` is a front panel whose face is no more than 3 mm from the furniture's front edge (doors, drawer fronts, frieze, strips); everything else is `body`. Internal drawer fronts behind a door count as carcass.
  - Doors are fronts with hinges: the hinge side is determined by their centres (`hinge`: left, right, top, bottom). Drawers are found by their runners: the drawer box is the panels above a runner between its ends, the front is the face panel in front of it (it can be wider than the carcass).
  - Handles are found by holes on a front: two or three collinear points give the axis, the midpoint and the hole spacing; the length, width and projection of a bar handle come from a table `{hole spacing mm: (length, width, projection)}`, otherwise hole spacing + 28 mm.
  - Carcass cells are found by guillotine cuts on the projection onto the front: a through upright splits a rectangle into columns, a through shelf splits it into tiers, until nothing is left to split by. Drawer boxes, fronts and back panels do not take part in the split; panels at least half the carcass deep are counted. A cell's depth runs from the front edges of the surrounding uprights and shelves to the nearest panel behind it.
  - `storage_from_bazis(m, мебель, ns, sections, names, hanging)` (where `мебель` is the furniture entity) creates storage locations: cells (`c1…` bottom to top, `hanging` means a hanging rail) and drawers (`d1…` top to bottom) per section, given as rectangles, or directly in the furniture. Names and aliases can be overridden by key.
- **Rendering**: `props.render.parts`: a box `{"b": [x0, y0, z0, x1, y1, z1]}`, an outline `{"p": [[u, v], …], "ax": thickness axis, "d": [from, to], "h": cutouts}` (points with ax "x" are (y, z), "y" are (x, z), "z" are (x, y)), or a cylinder `{"cyl": [x, y, z0, z1, r]}` (supports); `m` is the role and the colour key in `colors` (`body`, `front`, `back`, `legs`…). `handles_at` are the handles: ends `x`, `z`, front face `y`, mounting `posts`, width `w`, projection `d`. Storage locations inside such furniture draw nothing except a hanging rail (`rod_drop`: from the top of the cell, 0.06 by default).
- Materials in the designer files are sometimes not up to date (the decor is changed in the combined order file); the correct ones are in the cutting invoices, where part sizes are listed by decor.

### Documents on entities

Any entity has its own document base: manuals, design project and drawings, receipts, warranties, contracts, shop pages.

- **A document** is an entity of kind `document` (`docs.py`, IFC: `IfcDocumentReference`). Its parent is what it relates to (fridge, kitchen, cabinet). If a document also describes other things, it has `documents` relations (kitchen project → all its modules). Subtypes: `project` (design project, drawings), `assembly` (assembly or installation instructions), `manual`, `datasheet`, `receipt`, `warranty`, `contract`, `page` (web page), `photo`, `note`.
- **Link and copy.** `props.url` is where the document lives online; `props.file` is the local copy, a path from the root of the documents folder (`--docs`, `DATA/docs` by default); also `mime`, `size`, `pages`, `sha256`, `saved_at`. The copy opens even if the site has gone or been redone. The package stores only the path; the files sit next to the packages and are not needed in git.
- **Where it shows.** The card has a Documents («Документы») section: the entity's own documents plus those of the nearest parent that apply to the whole (`project`, `assembly`, `contract`): a kitchen drawer shows the kitchen project, while a receipt for a kitchen socket shows only on the socket. Parts inherit, but things stored in them do not: a phone in a drawer does not get the kitchen project. A document already among the entity's own (the kitchen project linked to its modules) is not repeated "from the parent". Document card: open the copy, download, go to the site, what it relates to; the copy buttons appear only if the server found the file in the documents folder (`copy` in the snapshot). Only what is open to the audience is visible and counted (`find`: «документов: N», "documents: N"); closed documents cannot be found even by id.
- **Adding from the viewer**: as a file (`POST /api/docs?to=…&title=…&type=…&filename=…`, body is the file, up to 50 MB; `filename` is required so that a `.json` file is not confused with a request) or as a link (`POST /api/docs` with JSON `{to, title, type, url, copy}`): with `copy`, the server downloads a copy itself: PDFs and images as they are, a page as an HTML copy with `<base href>`, converted to UTF-8 from its encoding. The copy's type is determined by content, not by URL: a PDF from a `download.php` page is stored as `.pdf`. Such documents are written to the items package and go to `trash.jsonl` when removed; when an item is crossed out, its documents go into the same trash line. `GET /api/doc/{id}` serves the copy from the viewer's address, and under ingress that is HA's own address, so nothing in a copy is executed: PDFs, images and text open in a tab, a page or SVG in a sandbox (`Content-Security-Policy: sandbox`), everything else (XML, office files, unknown) is download-only. The copy path never leaves the documents folder.
- **Page snapshots when building packages**: `python -m cherrybim.docs snapshot URL файл.pdf` drives headless Chrome over the debugging protocol to print the screen layout into a PDF with text, after removing pop-ups and overlays. Shops often hide the print layout entirely, so `--print-to-pdf` produced a blank page. `fetch` downloads a file as is.
- **Private numbers** (IMEI, serial number, MAC) are the `props.ids` dictionary on the item itself. It is not in search (only string properties are indexed) or in assistant responses; in the card the number is masked (the last 4 characters of a long one are visible, 2 of an 8–11 character serial, a short one in full); "show" is behind a button, and a second click copies it. For items in the items package, numbers are edited under Edit («Изменить»): one line per "name: number", a second IMEI is saved as "IMEI 2"; the name is up to 40 characters, the number up to 120.
- **Voice.** The MCP tool `documents(what)`: "what documents, manuals, drawings are there for …": names, types, whether there is a copy, links. `find` reports how many documents an entity has.

- **Plan image** (`plan.py`, 0.3). Pillow, drawn at double size and downscaled. The container is the location's apartment, otherwise the storey, otherwise the block. Only entities visible to the audience are drawn; furniture inside furniture is skipped from above. The plan gets onto a screen like this: the server puts a PNG into HA media and calls the `--show-script` script. What the script does next (for example, queues a request to the TV) is unknown to the core.

### Ideas (0.6)

What could be added, rearranged or removed in the home: see how it will look before buying and drilling. Anyone can write an idea (a person, the assistant); the owners respond with a status and notes.

- **File** `*.idea.json` (`ideas.py`, schema `schema/cherrybim-idea-0.1.schema.json`) sits in the ideas folder (`--ideas`, `DATA/ideas` by default). It has `add`: new entities (a shelving unit with storage locations, a shelf); `change`: edits to existing ones (`parent` and `placement` move it, `geom` and `props` are merged, `null` removes a key; `note` says why); `remove`: what will be removed, together with everything inside it, except what the idea moved elsewhere with an edit: the old shelving unit is removed and the things on it move to the new one, so they "will change" rather than "go". References are by id or key, including to new entities of the same idea. New entities can omit an id: it is `uuid5` of the idea key and the entity key.
- **A layer, not an edit.** An idea does not touch the twin's packages: the server assembles the "as it will be" variant on the fly (`apply`: edits as copies, new entities as a separate package) and caches it until a new twin version. This is an overlay in the spirit of IFC5 layers. A variant with a new entity that has no parent is not assembled (an error in the list), while an edit to something that no longer exists (the item was crossed out) is only a warning: the rest can still be viewed. A malformed file is not hidden: it appears in the list with the error text. An idea stricter than the audience (`privacy`, household by default) is not visible at all.
- **API.** `GET /api/ideas`: the list: name, summary, status, how many will be added, changed, removed, what it relates to. `GET /api/twin?idea=<ключ>`: a snapshot of the variant: entities carry an `idea` mark (`add`, `change`, `remove`), item editing is disabled, and `idea` in the response holds the description, the lists of new, changed and removed entities, and viewpoints in the site coordinate system. `POST /api/ideas/<ключ>` with `{status, note}`: status (`idea`, `liked`, `planned`, `done`, `rejected`) and a note; these are written to `state.json` in the ideas folder, not to the idea file: the file is the author's word, the state is the owners' answer, and rebuilding the ideas does not overwrite it.
- **Viewpoints** (`views`) are in the `about` coordinate system: eye, target, cutaway, field of view `fov`, and a width `fit` that must fit in the frame. On a narrow screen the camera backs off along the ray, but an inside view (with `fov` set) cannot back off, since there is a wall behind it, so the angle widens instead, up to 100°. A small room is seen better from inside with a wide angle, as in a photo; a top view without the cutaway suits a screen of any shape.
- **Viewer.** The Ideas («Идеи») button (if there is at least one idea) opens the list; an idea opens as a bar above the scene: Before / After («Было / Стало»; two snapshots, same camera), viewpoints, and New («Новое»): new and moved things in a warm tint of their own colours. What will be removed is not drawn in After (it is no longer there), and with New it shows as a red ghost next to what will replace it. The card has the description (`text`: paragraphs, "- " is a list item, "## " a subheading), links to the new things, the status, notes. The `#i=<ключ>` link opens an idea directly. On a phone the scene comes first; the description opens from the name on the bar.
- **Implemented**: the idea's entities are moved into the twin's packages (or into the inventory), and the idea is marked "done".

### Ready-made models (0.6)

An item that has its own 3D model, such as a 3D-printed holder or a small Multiboard bin, is drawn with it rather than with the per-type model. `mesh` geometry (`asset`: a path inside the models folder) has been in the model since 0.1, but the viewer did not draw it.

- **Files** are GLBs in the server's models folder (`--assets`, `DATA/assets` by default). `GET /api/mesh/<id>` serves the file only for an entity with `mesh` geometry that is visible to the audience; `?idea=<ключ>` for entities from an idea variant. A path outside the models folder gives "no such model".
- **From 3MF and STL**: `cherrybim.io_mesh` (the `mesh` extra: numpy) reads a 3MF assembly with components in other files of the archive (as Bambu and Orca produce) and build plate matrices, and binary and ASCII STL; it converts to metres, rotates (X first, then Y, then Z), puts the origin at the corner of the bounding box so the model extends along +X, +Y, +Z like a box; simplifies by merging vertices on a grid, coarsening it by 1.25× while there are more than `max_tris` triangles; writes a GLB: one mesh per part, colour and roughness as a material, coordinates already in the entity's system. `mesh_to_glb` returns the bounding box, useful for nearby storage locations. `python -m cherrybim.io_mesh ВХОД.3mf ВЫХОД.glb --rot-z 45 --color "#222222"`.
- **Viewer** (`mesh.js`) parses such a GLB itself, without GLTFLoader: vertices, indices, nodes with a matrix or TRS, material colour; normals with creases at 30° (printed parts are flat faces and fillets). The entity's group appears immediately, the meshes when the file arrives; the page is ready (`ready`) when the models have loaded, but after no more than 8 s. One colour for the whole model, `props.render.colors.body`: models for printing are coloured with the plastic they were printed in.

### Storage place preview (0.7)

Small things such as a stack of drawers on a table or an organizer on a shelf take up a couple of dozen pixels in the apartment scene: partitions and labels cannot be made out. So a storage place with its own model has a preview window.

- **What it opens** (`subjectOf` in `peek.js`): the selection or the nearest entity up the tree with `mesh` geometry, either a storage place or furniture that has places inside. An item is skipped (an item in a compartment opens its drawer); a room and anything above furniture do not open the window.
- **What is in it**: the model of what is shown, the models of everything inside (the stack's drawers), and the storage places inside as invisible volumes in its coordinate system. Direct places are labelled: a drawer in the middle of its front, a compartment or shelf on top; the text is `props.render.label` (lines separated by `\n`) or the name, no wider than the place on screen, and a narrow place shows only the first line. A free place (`props.free`) is in italics.
- **Selection**: a click on a place or its label selects it in the twin (the main scene's camera does not move); the selected place gets a frame and a highlighted label; "↑" goes to the furniture above, "×" closes the window until something else is selected.
- **Camera**: furniture from the front at 20°, a drawer from above (68°), like a layout diagram on paper; the distance is chosen so that the corners of the bounding box fit in the frame.
- **Implementation**: its own scene and its own WebGL context (on first show), lighting from a room environment and one light; no shadows and no ambient occlusion, so the window is cheap. Meshes come from the `mesh.js` cache shared with the main scene. Rendered on demand.
- **In the main scene**: a drawer with `render.pull` slides out by that travel while it or something in it is selected (with its compartments and items: the whole branch shifts towards the front); places inside furniture with its own model draw nothing, only the volume for clicking.

### Show director (`director.js`)

A camera that guides the viewer on its own: an orbit of the apartment, a flight into a room, a flight along the pipes at eye level, an approach to an item. For a screen without a mouse (TV, voice) and for tours.

- **Shots.** A frame is a function of time `pose(t) → {p, q, fov, roll}` (camera, look-at point, field of view, roll):
  - `Orbit`: an orbit in a circle (`w`, rad/s) or a `±sway` around the target, with the tilt "breathing" `±breathe`; the apartment orbit takes 140 s;
  - `Glide`: flight along a path with a precomputed speed profile;
  - `Still`: a fixed pose.
- **Transition** (`Blend`): an optimal "pan + zoom" flight (van Wijk, Nuij, 2003; as in `d3.interpolateZoom`): the target moves in a straight line and the distance to it changes so that the image moves past the eye at constant speed; on a long flight the camera itself pulls back and rises above the apartment, then comes in. Azimuth takes the shortest angle, tilt changes smoothly, and on a long flight (compared with the distance to the target) it also lifts by up to +16°. The weight is the minimum-jerk curve `u³(10 − 15u + 6u²)`: speed and acceleration are zero at the ends; long transitions use a smooth trapezoid: acceleration and deceleration on the same curve, constant speed in the middle (peak 1/(1 − ρ) of the mean instead of 1.875). Both shots keep moving during the transition, so an orbit already under way is not cut off; a flight along a route starts 1.6 s before the end of the transition.
- **Transition duration** (`fitT`) by dry run: the transition is precomputed at 90 points and stretched until the apparent speed fits within 0.5 of the target distance per second (moving straight at the target weighs √2 times less than sideways: the eye tolerates a dolly-in better), acceleration within 0.45 of the distance per s², gaze rotation within 30°/s, and lens zoom within 7°/s. The initial value comes from the target path, rotation and change of distance (1.9–5.4 s), capped at 20 s. Speeds in a transition scale as ~1/T and acceleration as ~1/T², so T is stretched by the worst excess (for acceleration, by its square root).
- **Framing** is exact for perspective: box corners in the camera basis; the distance is the smallest at which all corners fit in the frame with margins. The apartment orbit is checked around the full circle every 10°: the apartment is in frame at any azimuth. A room is shot from the direction of the apartment's centre, three-quarter view, 56° from above; an item from the front (the −Y front of the item or its holder) in three-quarter view; a low item from more steeply above, an item hanging high almost head-on; small things with room around them, so it is clear where they are.
- **Flight along a route** (`route`): the system's polylines (its `has_member`) are merged into a graph of nodes; route ends in the middle of other segments become tees. The start is the node that feeds the others (`feeds`, the inlet node), otherwise the end of the longest route. The legs of the flight are a graph traversal: branches shorter than 1.6 m are seen along the way; several long branches from one tee are taken in turn, the longest last. A leg's path has its corners rounded with arcs (`smoothPath`, up to 0.65 m), then is resampled every 2 cm and smoothed (±12 cm, three passes): curvature at the entry to an arc builds up gradually, like on a road transition curve, and lateral acceleration comes in without a jolt. The speed profile (`speedProfile`): up to 0.9 m/s; in turns, limited by lateral acceleration (0.35 m/s²) and yaw rate (0.62 rad/s); slower near devices; and everywhere such that the gaze turns no faster than ~29°/s (`gazeCap`: a pipe hairpin, turning towards a device); acceleration and braking no sharper than 0.5 m/s², starting and stopping with jerk no more than 0.8 m/s³; within a profile step the motion has constant acceleration, so speed has no steps.
  - The camera is 1.5 m above the floor but **to the side of the pipe** (`lateral`): towards whichever side is further from the room wall, no more than 0.95 m and no further than half the free space, smoothed along the path. Pipes run along walls and under windows, so a camera right above the pipe would scrape the wall and fly through the curtains. Over a wall between rooms the camera rises by 0.6 m.
  - The gaze is at the average of five points ahead (0.55–1.45 of 2.4 m; past the end of the path, further along the last direction): in turns it swings round early and smoothly. The head turns towards devices along the way with smooth weights (with several nearby, the gaze is between them; a "nearest device" would switch abruptly); towards the end of a leg the gaze shifts to the device at its end, and it does not look back to the inlet node at the start of a leg. Roll in turns is up to 2.5°, precomputed over the whole path and smoothed along it; the lateral offset and lift between samples use a Catmull–Rom spline.
  - Heating scene: a wide shot with a title and a mini-plan → the inlet node close up → flight legs (letterbox bars), each ending with a shot of the device at its end with a title → wide shot. Dashes run along the pipes: supply is warm, away from the node; return is blue, towards the node; pipes in the screed are seen as an X-ray.
- **Occlusion.** Furniture and appliances the camera drives into disappear, and whatever is between the camera and the target becomes semi-transparent. The check casts rays to the target (for an item, also to its top and upper corners) against bounding boxes, and for those hit, against the actual geometry every 4 frames (a bed's box is higher than the mattress, while the ray passes over it). Materials are swapped only for the duration of the frame (`beforeRender`/`afterRender`): the viewer loses nothing.
- **Selection.** A room gets its own light: a warm floor, a glowing outline along the base of the walls, and a light curtain fading towards the cutaway. An item gets a warm pulsing glow over its real colours. A drawer or an item in a cabinet uses the viewer's selection (the cabinet becomes transparent).
- **Overlay**: its own 2D canvas (`Overlay`): a title at the bottom left (heading and caption), labels on items with leader lines, a mini-plan in the corner (rooms, route, camera with a view cone), letterbox bars, vignette, fades. In the browser it is a layer over the scene; in the stream it is composited with the frame.
- **Clock.** `tick(now)` is page or stream time; shots and scenes run on their own time, which stops when paused.
- **Scene rebuild** (new data from the server) does not restart the show: shots and paths stay the same; what is redone is the highlight and selection that the viewer dropped together with the scene (`onRebuild`).
- **Commands**: `director.play({op, id, ids, title})`: `overview`, `room`, `object`, `route`, `group`, `tour` (all rooms in a loop, starting from the hallway), `auto` (a view chosen by what the entity is: apartment → orbit, room → room, system or pipe → route, finish → the rooms with it, anything else → item), `key` (◀ ▶: neighbouring room, ▲ ▼: closer and further, OK: pause), `stop`. The response is `{ok, op, title, sub, seconds}` for the voice reply.
- **`?tv=1` mode**: a screen with no panels or pointer, dark background, the director drives the camera, pixel density 1; `?ss=2` renders the frame at double size and the stream downscales it exactly by half (with MSAA ×4 that is 16 samples per pixel: thin edges and highlights do not flicker from a distance). `?autoplay=1` starts an orbit immediately.
- **Stream** (`capture.js`): the scene frame and labels are composited onto a canvas, WebCodecs encodes it as H.264 (GPU, `latencyMode: realtime`, Annex B), and chunks go out over WebSocket. There are exactly `fps` frames per second of real time, and the scene runs by frame number; if it falls behind, the following frames are drawn without pauses until they catch up with time (a TV has a 1.6 s buffer), and only when the lag exceeds 1.2 s does the frame number jump (that is a camera jump); a busy encoder is waited for, and frames are not dropped. The stream size is the canvas's on-screen size. `snapshot(t)` is a single frame as the screen will see it. What to do with the chunks (HLS for the TV) is unknown to the core.
